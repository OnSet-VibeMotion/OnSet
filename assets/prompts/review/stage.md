## {{STAGE:review}}：最终验收、试听与交付

候选成片必须通过以下检查：

### 机器检查

画幅、帧率、编码、像素格式、总帧数、音轨规格、可完整解码和第 0 帧封面这几项由一条命令完成，不要自己拼 FFprobe：

```bash
validate_video({"video": "<候选成片>", "audio": true, "expect_frames": "<冻结时间轴总帧数>", "decode": true, "check_frame_zero": true, "report_json": "production/final-check.json"})
```

不符项会一次全部列出。判断结果读 `report_json` 落盘的报告，`ok` 为 `false` 时 `problems` 数组里是全部不符项，`hints` 里是值得看一眼但不构成失败的观察（例如第 0 帧偏暗）。

### 整片复查

机器检查只看规格，拼接与混音之后才出现的问题要靠整片复查：

```bash
review({"video": "<候选成片>", "scenes": "scenes/", "out": "production/review"})
```

它比对音轨与视频流各自的时长，精确统计总帧数并与各镜头帧数之和比对（漏拼、重拼、掉帧都会被拦下），检查每个镜头交界两侧的帧，并把每个镜头的首帧、中间帧、末帧拼成联系表，每个交界再出一张前后各 6 帧的条带 `seam-NN.png`。判断结果读 `production/review/review.json`：`ok` 为 `false` 时 `problems` 里是全部不符项；交界处的纯色帧只进 `hints`，因为切黑、切白可能是有意的转场，要你看图确认。写了 `handoff` 的交界还会比对前一镜末帧与后一镜首帧：差异大到是两张不同的画面时进 `problems`，说明有一侧没照 `bridge` 画，重渲染没接上的那一侧；差异中等时进 `hints`，看对应的 `seam-NN.png` 确认。有音轨时它还会解码成片，测量积分响度、真峰与响度范围写进报告的 `loudness`，并与项目音频目标比对；偏离只进 `hints`，不影响退出码，但除非平台另有响度规范，出现了就回{{STAGE:mix}}重新混音，不要在成片上再叠一次规范化。

机器检查通过后逐页打开 `production/review/sheet-NN.png` 做视觉复查：相邻镜头的交接、可读性与画面密度是否合适，结尾是否停在合适的画面；再逐张看 `seam-NN.png`，确认每个交界的转场顺畅，没有一帧闪烁、跳变或停在入场中间态，并对照两侧镜头 `prompt.md` 声明的出场状态与入场状态：持续物件的位置、大小和状态是否真的接上了。发现问题只重渲染相关镜头，重新拼接、混音后再复查一次。复查报告与联系表纳入审批绑定的检查文件。

整片看一遍时，对每一处画面变化问一句：它是在澄清、证明、控制节奏还是加强情绪？说不出作用的变化删掉。同时对照 `treatment.md` 检查钩子、揭示和收束是否落在了预定的位置。

发现问题按这个顺序修：

1. 先定位它归哪个文件管：稿件、`treatment.md`、`scene-plan`、某个镜头的 `prompt.md`、`frame.md`、cue sheet 或混音参数。
2. 改那个源头，再重新生成它的下游，不在成片上打补丁。
3. 改了一轮没有变好，先回头修正对问题原因的判断，写进修复记录，再动第二轮；不要在同一个判断上反复加码。

命令覆盖不到、仍需另行确认的：

- 音频解码采样数和节目终点正确。
- 字幕、镜头和音效 cue 没有越界。
- 发布平台若有专用响度规范，按平台规范核对 `review.json` 的 `loudness` 实测值。
- 输入、候选、素材、日志和检查报告的 SHA-256 绑定一致。

### 人工试听

机器检查不能替代人工听感。发布前必须：

- 用耳机完整试听一次。
- 用手机外放完整试听一次。
- 重点检查断句、发音、人声清晰度、音乐遮挡、音效突兀、爆音、点击声和结尾硬切。
- 无法实际完成物理设备试听时，必须在检查表中标记“未执行”，不得假称通过，并明确建议发布前补做。

### 审批和原子交付

- 把最终候选及所有检查文件的 SHA-256 写入 `production/approval.json`；`treatment.md` 与 `scene-plan` 一并绑定，它们改动后已批准的候选随之失效。
- 只有审批绑定全部通过时，才允许交付。
- 当前目录已有 `final.mp4` 时，先保留为带版本或时间标识的备份。
- 使用同文件系统内的临时文件和原子重命名生成根目录 `final.mp4`。
- 原子替换后再次检查 `final.mp4` 的哈希、规格和完整解码。

### 修订版与候选生命周期

- 每次修订使用独立 revision 或 attempt 目录，保留上一版视频、日志、检查报告和 SHA-256。
- 每次声称“已经修复”前，必须实际生成新的候选 MP4，并汇报新路径、修改时间、规格和 SHA-256；没有新视频不得只凭源码或截图宣称完成。
- 用户审阅的是明确绑定哈希的候选。预览通过后才能执行高质量渲染；高质量渲染不得改变已批准的时间轴、文字或布局。
- 只修复受影响镜头，其他已冻结镜头必须按帧数和哈希复用。拼接后仍要重新执行全片语义和机器 QC。


### 成片之后的局部修改

候选成片出来以后，用户提的修改大多只涉及一小块：一个字的读音、一句话的措辞、一个镜头的画面、一段配乐的音量。从被改的源头往下游走，只重做真正变了的部分，其余按帧数和哈希复用。「没变」要拿证据说话（前后的起止帧、哈希、对齐结果），不要凭感觉。

| 改了什么 | 要重做的 | 不用重做的 |
|---|---|---|
| 读音（字幕不变） | 在终稿里加 `<显示\|朗读>` 标记或改发音控制，见{{STAGE:voice}}；只重新合成受影响的那一句或那一段，按原位置拼回整条配音；重新对齐，`align_build()`；`scene_cues()` | 稿件审核（显示的字没变）、分镜审核、整篇配音、起止帧没变的镜头 |
| 一句话的措辞（字幕要变） | 改终稿那一句；只重新合成这一句或这一段并拼回；重新对齐、`scene_cues()`；含这句字幕或短语的镜头 | 分镜审核、整篇配音、其余镜头。稿件不重审全文，只请用户在口播稿页看改的那一句 |
| 一个镜头的画面 | 改那个镜头的 `prompt.md`（或它点名的素材），`scene_run({"scene": "<镜头目录>"})` 只渲染这一个，按{{STAGE:visual-qc}}看这个镜头；重新拼接静音母版，再把它与已有的混音合成候选 | 配音、对齐、`scene_cues()`、其余镜头、混音参数 |
| 配乐、音效、响度 | 只回{{STAGE:mix}}重新混音并合成候选 | 镜头、拼接、配音 |

重新合成配音时：

- 用同一个音色、同样的参数（语速、语气指导），只合成受影响的句子或段落。整篇重录会让别处的语气与时长一起变，后面的时间轴全部作废。
- 拼回原位置时，新旧片段的时长差尽量吸收在这句前后的停顿里，让后面的时间轴不动。吸收不了时，后面所有字幕与镜头都会平移，要重渲染的镜头会多很多：先告诉用户代价与替代做法（例如缩短这句的措辞），再动手。
- 拼接后保留修改前的整条配音与这一句的前后对比片段（各截几秒），交给用户试听。

判断哪些镜头要重渲染：

- `scene_cues()` 前后逐个比对镜头的起止帧。起止帧变了的、画面里烧了被改那句字幕或短语的镜头要重渲染，其余不渲染。
- 只重渲染这几个时用 `scene_run`，一次一个，不要用 `"force": true` 跑 `scene_run_all`：它会把所有被判为 Stale 的镜头一起重渲染。

收尾：

- 每次局部修改都要出新的候选，按本阶段重跑 `validate_video` 与 `review`，复查报告要跟上新的候选，用户在客户端里看到的进度才对得上。
- 汇报时写清这次重做了哪几步、重渲染了哪几个镜头，以及哪些没动、凭什么判断没动（例如「其余 23 个镜头起止帧不变」），并附上前后对比让用户确认。
- 已经确认过的稿件审核、分镜审核不用重新走：只有显示的文字或分镜计划真的变了，才请用户确认变了的那一处。
