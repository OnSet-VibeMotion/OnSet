# Windows 制作可靠性与耗时修复

本轮以 `34e105a` 为主线基线，修复 Windows 工具调用、字幕对齐、镜头排队与本地启动的实际故障。配音、分镜、字幕、完成镜头和批准文件不参与源码迁移或替换；部署只在所有制作会话及渲染任务空闲时进行。

| 故障 | 实现与边界 |
| --- | --- |
| `windows_inspect` 不接受新参数，音频摘要受小文件限制 | Windows 工具声明 `hash_files`，按流读取，单文件上限 256 MiB、总计 512 MiB；校验项目边界与凭据路径。工具和提示词使用同一次构建的资产快照。 |
| 对齐访问个人缓存、远端下载失败、反复猜测字幕时间 | Windows 专用 `windows_align` 使用已准备的本地模型和 Python，关闭更新；固定规范化过程保留全部朗读字符，一次推理、映射和独立音频能量校验。失败保留诊断，同输入默认不重试；成功结果按输入与输出摘要复用。 |
| FunASR 导入时间过长 | 时间戳进程只注册 MonotonicAligner 所需的七个组件模块；保留正常 Python 导入与真实模型，不改第三方安装文件。注册失败直接报告；目录枚举器在包初始化后恢复。 |
| 1、4、9 完成后仍有空位 | Windows 的 `scene_run_all` 增加 `priority_scenes`，全部批准且冻结的镜头一次入队，优先代表镜头，worker 完成即取下一项。`jobs` 仍读取用户设置并受资源预算限制。JSONL 记录派发、完成、并发与槽位空闲时间。 |
| 抽一帧却重复定位与解码 | 纳入用户另行授权的抽帧补丁，仅 Windows 用一次 FFmpeg 同时输出 PNG 和整帧灰度像素。裁剪只影响 PNG，保留自动选流与统计口径；macOS/Linux 继续原来的两次调用。 |
| 同一镜头被重复启动 | Windows 单镜头租约在启动模型之前拒绝重复任务；只清理自己的租约，保留归属不明的记录。已有活动任务和媒体不受影响。 |
| junction 清理报目录错误、产生伪 Stale | Windows 仅移除经 `lstat` 确认的目录链接，不遍历技能目标；来源解析忽略有制作标记的临时链接。真正的技能内容或输入变化仍按原指纹规则标为 Stale，不自动覆盖成片。 |
| 复查或修订候选被计作第十个镜头 | Windows 存在明确目录计划时，只统计计划内目录，按 Windows 规则忽略路径大小写；无目录计划的项目保留原发现规则。未被计划引用的 `production/visual-qc` 目录也跳过，素材与证据仍保留。 |
| `phrase_id` 列表导致 Python 字典键异常 | 固定 Windows 生成约定：`phrase_id` 为字符串或 null，多个来源另记；归一化脚本先检查类型，不任取首项、猜时间或改成装饰逃过校验。实际项目中已修正的脚本在隔离副本重跑，146 条事件通过，原文件摘要不变。 |
| 不可用模型被当成会话损坏而重试 | Windows 对 `model_not_found` 等明确不支持模型错误停止相同模型的重开会话；保留真正会话丢失的恢复路径，不改变用户模型选择或登录配置。 |
| Windows `git` 占位命令、缺少 `shasum`、无仓库被当故障 | 环境优先实际 `git.exe` 所在目录；Windows 使用 `Get-FileHash`。独立视频目录未初始化 Git 是正常状态，不初始化仓库或修改系统文件。 |

首次风格选择另有 Windows 本地操作路径：仅匹配界面生成的精确选择，调用现有风格安装操作；已有风格、批准分镜或完成镜头继续走原流程。本地操作的真实回执会加入下一轮模型上下文。可选推理强度设置只有显式环境变量才生效，未默认降低模型推理强度。

实测记录均为本机局部测量，不代表整片制作获得相同比例的加速：

| 测量 | 结果 | 可说明的范围 |
| --- | --- | --- |
| 已确认的 95.68 秒配音，完整字幕流水线 | 已安装版本末次复测 9.46 秒，同输入复用 0.17 秒 | 包含本地模型、映射及独立字幕校验，原配音和项目输出不覆盖 |
| 原生 Python 同音频结果比较 | 完整导入温热复测 14.68 秒；组件导入 6.89 秒，时间戳逐项一致 | 组件选择的局部收益；不同轮次的系统缓存与负载仍影响时长 |
| 原导入慢启动 | 全流程 144.50 秒，其中导入 130.20 秒 | 实际复现导入开销，不将冷、热缓存差异全部归因于代码 |
| 九个真实 Chromium/FFmpeg 渲染 | 全部成功、最多三个并发、无重复；补位最大空闲 0.074 ms | 使用小型隔离测试合成，并故意阻塞 4 号槽位；不含 AI 编写镜头和人工审查 |
| 实际 1920×1080 镜头的 12 帧抽取 | 三轮交替计时中位数 3.008 → 2.061 秒，减少 31.47% | PNG 与统计逐项一致，原视频摘要不变；记录来自另一个获授权聊天，统一部署前另通过 46 项媒体验证和 13 项 CLI 验证 |
| 浏览器硬件路径 | GPU 取帧约 6.6–7.4 秒，编码约 0.1–0.2 秒 | GPU 已用于画面；更换编码器无法消除数分钟的模型、检查和返工时间 |
| 原制作镜头日志 | 每镜头约 336–620 秒，其中原生渲染约 16.5–28 秒 | 总耗时还包含模型写代码、检查、失败调用和返工，不能全部称为网络等待 |
| 首次风格安装路径 | 真实本地操作约 0.69 秒，模型调用为零 | 仅限首次精确选择；历史模型操作约 59 秒，属于流程对照 |

本轮定向验证：原补丁引擎 114 项、CLI 34 项、启动器 3 项，加上抽帧引擎 46 项、CLI 13 项，共 210 项通过；另跳过一项原有的 macOS/Linux 物理内存读取测试。四组类型检查与隔离构建通过。主线同步提供的 18 项既有单元测试失败记录不视作本轮已修复，也不据定向通过宣称全套单元测试全绿。

Windows 本地开发重新构建时，通过 `node scripts/start-local.mjs --rebuild` 同时重建 CLI 与客户端，并自动记录配套资产；下一次普通启动继续使用该快照。正在制作时先等空闲，避免直接覆盖它仍在使用的构建文件。macOS/Linux 保持原启动与执行规则。

详细计时、摘要、失败诊断、保护文件清单和本地模型路径留在本机验证目录；不随源码上传模型、凭据或私人视频工程。源码提交中的测试分别覆盖 Windows 平台边界、不可变输入、候选篡改、失败不重试、真实字幕能量校验、优先派发、补位、租约及重建后再次启动。

补充落地检查：全部制作空闲后替换运行包，三个项目共 6,509 个保护文件摘要保持不变。真实 Windows 界面显示示例项目 `9/9`、时间线 `01:37`，不再计入修订目录中的整片复查副本；镜头发现、进度、分镜相关 27 项测试通过，macOS/Linux 的发现行为保留。

从应用「记忆」与「进化」页读取到三次字幕对应问题、一条待考试经验，尚无通过对照考试的经验。优化因此聚焦固定的字幕映射与校验、复用已验证结果、避免整批等待和重复抽帧。页面中不同批次镜头的平均时间不作为同条件提速证据，也没有自动启动额外的模型考试或把待考试经验当成已验证收益。
