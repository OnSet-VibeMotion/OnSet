# 第三方插件

> 从仓库根 `AGENTS.md` 拆出的开发约定。总则、命令与各份文件的索引见根 `AGENTS.md`；文中「见「某节」」指的节都能从那份索引找到。

第三方站（第三方插件；`flow/` 下按职责分文件：`manifest.ts` 清单类型与字段分级、`parse.ts` 解析、`lock.ts` 项目的锁文件（只有新建时记下的流程）、`installed.ts` 用户级的已装插件清单、`fetch.ts` 来源与下载、`staging.ts` 装与升级的两步（暂存、给用户看、装上或取消）、`load.ts` 读出全部插件（`loadStations`）与读不出来的插件参与了哪些制作（`brokenParticipants`）、`update.ts` 装、去掉与升级、`builtinplugins.ts` 内置插件、`promptparts.ts` 第三方站的阶段补充与说明、`skills.ts` 渲染技能；`external.ts` 只做转出，执行在 `run.ts`）是用户自己装的插件，onset 不分发、不维护，第一个用例是自动发布。插件装在用户级，装一次对这台电脑上的所有项目生效，和内置插件一样常在；项目里只记「这个项目选了什么」（新建时的流程、配音与对齐取值、镜头的 `plugin_skills`、整片风格）。写给插件作者的说明是 `docs/plugin-authoring.md`：

| 约定 | 原因 |
|---|---|
| 一个站是一个目录加 `onset-station.json`，只能声明：提示词文本、站点（`outputs` / `stale_after` / `gate_files` / `state` / `guide` 声明式判断）、`produces`、操作。清单严格校验：路径只能是项目里的相对路径，不能声明 `production/studio/`、`.agents/`、`.env` 这类 onset 自己的文件，id 不能与内置站重名 | 第三方代码不进 onset 的进程，能做什么全写在清单里，添加时给用户看得见 |
| 清单有格式版本 `manifest_version`（缺省 1，`flow.ManifestVersion`）与可选的 `requires.onset`（最低 onset 版本，semver）：格式更新时先于「不认识的字段」报「要更新的片场」；比较用的版本取 `version.compatVersion()`：客户端主进程启动时用 `app.getVersion()` 设的宿主版本（`setHostVersion`），没有再退回工具版本（`setToolVersion`，与 `onset --version`、渲染指纹同源）；不是 x.y.z（本地构建 dev）时不查最低版本。版本存取在不依赖任何功能包的 `packages/engine/src/version`，`scene/record.ts` 只转出，flow 不 import scene。**客户端不调 `setToolVersion`** | 趁还没有第三方用户把兼容面收住；旧 onset 读到新清单要说清楚该做什么，而不是列一串不认识的字段。客户端是主要交付物，进程内后端也得查；工具版本进渲染指纹，客户端改它会让进程内算的指纹变 |
| 顶层字段分「稳定 / 实验性」两档（内置插件与第三方站用同一份字段，没有内置专用的），唯一来源是 `flow.ManifestFields`：解析器的已知字段从它来，`experimentalFields` 按它报告一份清单用到了哪些实验性字段（设置页「详情与设置」与 `station_add` 输出照实写「以后的版本可能调整」，内置插件不标）。`docs/plugin-authoring.md` 的「顶层字段」表与它一一对应，`manifest.test.ts` 的「lists exactly the top-level fields the parser accepts」核对；加字段要同时改表、改文档 | 稳定字段承诺不改意思；实验性的先让作者与用户知道可能会变 |
| 站目录摘要（`treeDigest`，`digest.ts`）按目录缓存在进程里：每次先 stat 整棵树（路径、大小、mtime、ctime、inode），概要变了才重读重算 | `loadStations` 到处都在调，每次全量读 git 来源的站太浪费；缓存只省读文件，不放过任何改动（`manifest.test.ts` 的「still refuses a station whose content changed」） |
| 装与升级都两步走（`flow/staging.ts`）：`station_add` / `station_update`（客户端 `POST /api/stations`、`POST /api/stations/{id}/update`）只把插件取到 `<stationsDir>/.staging/<编号>/`、校验清单，给出 `flow.StationPreview`——操作（AI 能用的工具与要用户点的按钮，附 `OpsTrustNotice`）、页面权限（project / network / uses / 读哪些文件）、实验性字段、钩子与定时、渲染技能（`scenes: all` 时 `rerender_all`）、带来的做法与风格库、顶替或接在哪一站，升级另带版本、commit、新申请的权限与新用到的实验性字段的差异；不写 `installed.json`、不参与任何项目。用户看过点「装上 / 换上」才走 `station_install`（`POST /api/stations/staged/{编号}/install`，git 来源再核对一遍摘要，看过之后被改的不装），取消走 `station_discard`（`…/discard`）清掉暂存。客户端里取回是后台任务，预览经任务的 `result` 交给设置页的确认（`StagedConfirm`）。`flow.installStation` 不经确认，只给测试与引擎内部用；`link:` 来源不用更新。既没装也没取消的暂存目录放过一天（`StagingMaxAgeMs`），下次取插件时清掉（`sweepStaging`） | 插件对所有项目生效：在用户看清它要什么之前就装上，等于替用户做了决定；升级也要让用户看见插件多要了什么 |
| 插件中心（`flow/market.ts`，后端 `studio/market.ts`，界面 `Market.tsx`）：独立的目录仓库 `OnSet-VibeMotion/onset-plugins` 的 `index.json`（`schema: 1`，`parseCatalog` 严格校验认得的字段、**忽略不认识的字段**：所有装出去的客户端读同一份目录，加字段不能让旧客户端读不了；改了已有字段意思才递增 `schema`。拒收不认识的字段是插件中心 CI 的事），每个插件写来源（不带 `#ref`）与若干版（`version`、`ref`、40 位 `commit`、`requires_onset`）；`pickVersion` 按 `version.compatVersion()` 挑能装的最新一版，`marketItem` 和已装插件比出 available / incompatible / installed / update / other_source / builtin（按 `repoKey` 认同一仓库，换仓库不给升级）。`GET /api/market` 立刻给缓存（`<stationsDir>/.market/`），缓存超过 `CatalogMaxAgeMs` 在后台刷新（`startRefresh`，不建任务、不占写锁），失败照实给 `error`、保留旧目录；`POST /api/market/install`、`/update` 只收 `{id, commit}`，来源由后端从目录算，起的仍是 `station_add`（带 `expect_id` / `expect_commit`）与 `station_update`（带 `source` / `expect_commit`）：取回后 `checkExpect` 核对 id 与 commit，对不上清掉暂存报错；之后照旧是 `StagedConfirm` 与 `station_install`。目录的版本另可写 `digest`（GitHub 压缩包的内容摘要，与 `treeDigest` 同一算法）、`yanked`（撤回原因），插件可写 `deprecated`（不再维护）与 `maintainers`（客户端只显示）：撤回的版本 `pickVersion` 不挑，装着它的显示原因并给换（版本号更低也换）；不再维护的不给新装（`unavailable`），装着的照常用、显示原因；后端对两者的安装请求回 409。有 `digest` 时后端把它作为 `expect_digest` 交给 `station_add` / `station_update`，执行进程先用 curl 下 `codeload.github.com/<仓库>/tar.gz/<commit>`、tar 解开、核对摘要（`flow/archive.ts` 的 `fetchArchive`，不用 git），再交给暂存（`stageStation` / `stageUpdate` 的 `prepared`）；下不来或对不上时有能用的 git 就退回克隆（照旧核对 commit），没有就报两边的原因。插件中心仓库的 CI 用同一份压缩包算摘要（`scripts/lib.mjs` 的 `treeDigest` 与引擎逐字节相同），并按 PR 作者核对 `maintainers`；`scripts/bump.mjs` 与可复用工作流 `bump.yml` 让插件仓库推 tag 时自动发「加一版」的 PR。图标、截图经 `/api/market/images/…` 由后端代取（按文件头只收 PNG / JPEG / WebP，不收 SVG），界面不直接连外网。联网经 `market.useHttpFetch`：客户端主进程注入 Chromium 的 `net`（`apps/desktop/src/main/network.ts`，缺省系统代理，设置了 `NETWORK_PROXY` 用独立会话），没注入用全局 `fetch`；`file://` 目录直接读（开发与 e2e，e2e fixtures 把 `PLUGIN_CATALOG_URL` 指到沙箱里的空目录）。默认依次试 raw.githubusercontent 与 jsDelivr（`DefaultCatalogURLs`）。`market.test.ts`、`studio/market.test.ts`、`Market.test.tsx` 与 `stations.spec.mjs` 的「plugin center」钉着 | 不另造安装路径：插件中心只是「去哪找来源」，看清再装的约定一样成立。不用 git 的那条路是因为客户端用户的 Mac 上可以没有 git（「开箱即用」），curl 与 tar 是系统自带的；撤回比删掉登记好：删掉之后装着的人什么都收不到。来源不收界面给的，免得页面借插件中心装任意地址。国内连 raw.githubusercontent 常常不通，jsDelivr 多半能通 |
| 只属于这台电脑的设置（`config.MachineKeys`：`NETWORK_PROXY`、`PLUGIN_CATALOG_URL`、`UPDATE_FEED_URL`）也写在 `settings.conf`，但不进 `config.load`、没有「这个项目」一栏（`config_set` 与 `/api/settings/project` 拒绝），经 `config.machineSetting` 读（同名环境变量优先），设置页「网络与更新」（`MachineSettings`）。`NETWORK_PROXY` 给取插件的 git 用 `flow.withGitProxy`（`GIT_CONFIG_PARAMETERS`，与 `onset setup --proxy` 同理只给 git，盖过 `stationproxy.ts` 按系统代理设的 `https_proxy`）；git 子进程另带 `GIT_HTTP_LOW_SPEED_LIMIT/TIME` | 代理、目录地址是机器的事，不随项目走；写进项目会被拷到别人的电脑 |
| 已装插件记在用户级的 `<数据目录>/onset/stations/installed.json`（`flow.InstalledFile`，`ONSET_STATIONS_DIR` 覆盖，`childEnvironment` 在会算出另一个目录时显式传）：来源、版本、commit、内容摘要与它在制作里出现在哪（`InstalledRole`：带不带流程、顶替或接在哪个站点后面、有没有站点）。git 来源按 ref 克隆、记 commit 与内容摘要，存进 `<数据目录>/onset/stations/<id>/<commit>`，摘要对不上就不用；`link:` 是开发用的本机目录，不核对。不接 npm。项目锁文件（`flow.LockFile`）不记插件：读到旧的 `stations`、`flow` 字段直接忽略。`station_add` / `remove` / `update` / `list` 不带项目；客户端的 `/api/stations` 列表、装、去掉、更新、设置不要打开项目，装、去掉、更新是不占项目写锁的后台任务（`studio/tasks.ts` 的 `runUserOp`），执行操作、页面读文件仍针对当前项目 | 同一份已装插件 + 同一个项目两次制作要得到同样的说明；npm 包装一次就执行了 install 脚本。插件不按项目走是项目主人的决定：装一次到处能用，首页新建时就能选到它的片型与风格 |
| 提示词：`runPrompt` 把各站说明接在最后（`flow.extraPrompt`），每站一节，声明「与上面的约定冲突时以上面为准」。读不出来的插件只在参与这个项目的制作时（流程是它带来的、它顶替了流程里的站、它的站点接进了这条路线——写了 `after`，或没带流程；按装上时记的 `InstalledRole` 判断，`flow.brokenParticipants`）让「开始制作」报错；其余的进 `RunPromptResult.warnings`，客户端在那次整片制作的对话里发 notice，设置页「我的插件」列出问题并给「更新 / 去掉」 | 参与制作的插件悄悄少一步更糟；但插件对所有项目生效，一个坏插件不该让与它无关的项目都开不了工 |
| 操作在子进程里跑（`flow.runStationOp`）：工作目录是项目根，stdin 一行 JSON，最后一行 `onset-result <JSON>` 是结构化结果；环境只给 PATH、HOME、语言、代理、证书与 `ONSET_STATION_DATA`（插件自己的数据目录，凭据放这里），项目 `.env` 一概不传 | 发布插件要读成片，但不能拿到配音、模型服务的凭据 |
| 操作**不是沙箱**：它是用户电脑上的普通程序，能读写用户的文件、能联网（HOME 照传，很多工具离了它不工作）。`runStationOp` 前后各扫一遍项目树（`flow/scope.ts`，只 stat；跳过的目录与轮次快照同一张表 `fsutil.ProjectSkippedDirs`，但项目根的 `.agents` 照扫，`production/studio` 里客户端自己边跑边写的状态不算），变了的文件不在 `produces` / 站点 `outputs` 里的算越界：写进操作输出末尾、结果的 `out_of_scope`（最多 20 条加 `out_of_scope_more`）；写到 onset 自己的文件（`ReservedPrefixes`，与清单校验的 `reservedPrefixes` 同一份）时操作按失败处理，照实说文件已经写了、只能回退那一轮或用 git 恢复。客户端启动的操作仅由宿主扫描。同一项目有其他写入者重叠时只检查保留文件（除客户端自动追加的编排用量账本），有改动就把本次操作标为失败并说明归属不明，记在任务的 `warning`、`last_run` 上，钩子与定时触发的另在最近的对话里发 notice。添加时（`station_add` 的输出、设置页的添加确认与详情）用 `flow.OpsTrustNotice` 这句话说清，页面的权限另列 | 设计稿承诺过越界写入要标出来；清单里的权限只管得住页面，混在一起写会让用户以为操作也受限。不做文件系统沙箱 |
| 运行时：`command` 第一个元素写 `{node}` 用 onset 自己的运行时（`toolpath.nodeCommand`，客户端里是 Electron 带 `ELECTRON_RUN_AS_NODE=1`），写 `{python}` 用 onset setup 经 uv 装进 `<数据目录>/onset/python` 的 Python（`flow.managedPython`，没有就抛 `prereq.MissingError`，不现下载）；后面第一个参数是脚本，相对路径按站目录解析。裸写 `node` / `python3` 照旧按 PATH 找，找不到时报错提示改用占位符。站目录在 `"type": "module"` 的包里时脚本要用 `.cjs` 才能 `require`（假发布站就是这样） | 客户端用户的电脑上可以没有 Node 与 Python（见「开箱即用」） |
| `trigger: agent` 的操作由工具服务登记成 `x_<站>_<操作>` 工具（`toolsmcp.externalOps`，所有项目都有，执行时落到 `station_run`）；`trigger: user` 的只在界面上出按钮（设置「功能与插件」里每个插件的「详情与设置」，是盖在设置窗口上的弹窗（`Stations.tsx` 的 `PluginDialog`，挂到 body 上，Esc 只关这一层），与插件的设置、页面入口集中在一处；不放进发布页这类制作页面，也不在项目里另开插件页；`POST /api/stations/{id}/ops/{操作}`）。缺省要打开项目才能点；清单写了 `project: false`（实验性，登录、管理账号这类插件自己的配置）的没打开项目也能点，这时 `project_root` 为空、工作目录是插件的数据目录、不扫越界、不占项目写锁，是用户级的后台任务（`studio/stations.ts` 的 `runUserStationTask`），打开了项目时照常在项目里跑。`list: true`（实验性）的操作返回 `items`（标题、说明、只认 `data:image` 的头像、每项的按钮与确认语），弹窗打开时与这个插件别的操作跑完后自动执行、画成卡片（`PluginActions`），它只该读插件自己的数据，所以一律按用户级任务跑、打开了项目也不占写锁——不然用户随后点的项目操作会被「项目正忙」拒掉；插件操作交给任务 `result` 的只有插件那句 `message`（`stations.ts` 的 `taskResult`），列表结果不进任务——任务连同 result 会写进打开着的项目的 `production/studio/tasks.json`，账号昵称、头像不能跟着项目被拷走；`form: false`（实验性）的操作不出按钮表单，只给卡片按钮与插件页面调。插件的客户端内网页（`apps/desktop/src/main/station-browser.ts`）每个账号单独一个窗口（登记在 `pluginwindows.ts`，找主窗口、「主窗口关了就退出」都跳过它们），另有 `hint`（工具栏上的一句话）、`state`（还开着、还在前面吗：用户点「返回片场」收起窗口就算不在前面）、`busy`（自动操作时盖半透明遮罩显示说明与进度，挡住用户的鼠标与键盘，连接撤销时自动揭开；有遮罩时关窗口先确认）、有插件页面开着时每 `FlushIntervalMs`（5 秒）把它们的本地存储与 cookie 落盘（网站随时写的草稿几秒内就到磁盘，崩溃或被强退时少丢，但两次落盘之间的修改仍可能丢；实测 Chromium 自己会让磁盘落后几分钟）、关页面（用户点关闭、插件关、移除账号）与退出时先把窗口藏起来，网页在后台正常走完关闭流程（`close({ waitForBeforeUnload: true })`，最多 `UnloadGraceMs`），本地存储落盘后才销毁窗口；退出由 `before-quit` 等它们关完（已经开始关的页面也等，完成前重复退出复用同一次等待）、`forget` 等页面销毁完成后再清账号存储与缓存（先清的话，关闭流程里写的草稿会被写回来；清理期间拒绝重开该账号——同目录复用同一 Session，会伤及新页面）、打开与跳转在 `dom-ready` 就交回插件（`loadUntilReady`，抖音整页加载完要 3–4 秒、结构就绪不到 1 秒）、片场替插件跳转或关闭时放行网页的「确定要离开吗」（`will-prevent-unload`，用户自己在网页里点的照常问）、`close`（关掉本次的页面）与 `forget`（关掉某个账号开着的页面，移除账号前用），登录这类「等用户在网页里做完」的操作靠它们自动收尾。用了网页的用户操作（清单有 `browser`、`trigger: user`，`stations.ts` 的 `sharedStationOp`）不占项目写锁，登记成 `Server.beginShared`（重启装更新前照样列进 `activeWork`）：执行进程不扫越界（`station_run` 的 `host_scope`），由 `runStationTask` 扫；期间还有别的写入者（写锁、另一个这样的操作，`Server.otherWriters` 与 `writeEpoch`）就不报越界、也不按写了片场文件判失败，只有它一个在写时照常检查（`stations.test.ts` 的「runs browser ops without the project write lock」）。`station_add` / `station_install` / `station_discard` / `station_remove` / `station_list` / `station_run` / `station_update` 的 scopes 只有 cli | 发出去、上传这类对外且不能撤回的动作只能由用户点；加不加第三方插件是用户的决定，编排工具不能自己装。网页单独开窗、不占写锁：上传大视频要等很久，不能挡住片场，也要能几个插件同时上传；改动分不清是谁写的时候宁可不报，不冤枉插件。抖音的编辑页只在 beforeunload 里把编辑内容存成草稿，直接销毁页面（`waitForBeforeUnload: false`，实测不触发 beforeunload，`station-browser.spec.mjs` 换回旧写法会失败）草稿就丢了 |
